# 需求与领域设计

## 1. 产品范围

### 1.1 产品目标

系统服务于单所高校的学生社团业务，统一管理社团申请、成员、活动、签到、经费、通知、评价和审计，减少线下表格与口头审批造成的信息不一致。

### 1.2 首个可交付版本

首个版本提供可独立运行的完整校内闭环：

- 本地账号注册、登录、刷新会话、退出和个人资料维护。
- 游客浏览已公开的社团和活动。
- 社团申请、学校审核、资料维护、部门与成员管理、注销申请。
- 活动申请、学校审核、发布、报名审批、二维码签到、总结和评价。
- 经费申请、分级审批、收支记录、预算汇总和 CSV 导出。
- 站内通知、首页角色化待办、基础统计、意见反馈、成员/财务 CSV 导出和审计日志。
- 社团申请材料、活动总结和财务凭证附件；移动浏览器可调用系统相机选择图片。
- 桌面与移动浏览器响应式适配，移动端使用底部主导航。

邮箱验证码、短信、校园统一认证、第三方 OAuth、自定义角色编辑、通用数据导出、通用文档库、Redis、消息队列和全文检索属于扩展能力；首个版本预留边界但不伪装成已经接入或实现。

### 1.3 不在首个版本内

- 跨高校多租户和校际数据共享。
- 真实支付、银行拨款或电子发票核验。
- 原生 iOS/Android 应用。
- 人脸识别、定位打卡和自动生成财务凭证。
- 由系统替代学校线下法定审批或档案制度。
- 可由普通管理员在线编辑的任意权限表达式；首版使用经审计的固定全局角色和社团岗位。

## 2. 用户与角色

系统权限由“全局角色 + 社团内岗位”共同决定，避免把某个社团的负责人提升为全站管理员。文档中的“社团负责人”仅指该社团的主席或副主席；“部门负责人”是原讨论中“部门主席/部长”的合并规范名称，界面可按学校习惯显示为“部长”。“活动协办者”是由活动创建者从本社团有效成员中显式指定的活动级岗位。

| 角色 | 作用域 | 主要职责 |
|---|---|---|
| 游客 | 公开数据 | 浏览已批准且公开的社团、活动 |
| 学生 | 本人 | 维护资料、申请社团、报名活动、查看通知、提交评价反馈 |
| 社团成员 | 指定社团 | 访问社团内部通知和成员能力 |
| 部门负责人 | 指定社团部门 | 管理本部门成员与活动协作 |
| 副主席 | 指定社团 | 协助管理成员、活动和经费申请，不能移交或注销社团 |
| 主席 | 指定社团 | 管理社团资料、部门、成员、活动、经费和负责人任命 |
| 学校管理员 | 全校业务 | 审核社团、活动、经费与注销，处理反馈和查看统计审计 |
| 超级管理员 | 系统 | 管理学校管理员、全局配置、用户状态和全部审计数据 |

约束：每个有效社团恰有 1 名主席，最多 2 名副主席；每个有效部门恰有 1 名部门负责人。负责人必须是该社团的有效成员。角色调整采用事务并写审计日志。

## 4. 核心业务规则

### 4.1 账号与会话

- 用户名为 4 到 32 个字符，只允许字母、数字、点、下划线和连字符；邮箱在系统内唯一。
- 密码最少 8 个字符，必须同时包含字母和数字；仅保存自适应哈希。
- 连续 5 次登录失败锁定 15 分钟；成功登录后清零失败计数。
- 访问令牌有效期 15 分钟，刷新令牌有效期 7 天且每次刷新轮换；退出、冻结或修改密码后撤销相关刷新令牌。
- 禁用用户不能登录，已有会话在下一次受保护请求或刷新时失效。
- API 不返回密码哈希、刷新令牌摘要和内部安全字段。
- 修改密码必须验证当前密码，完成后撤销该用户全部刷新令牌。用户可申请注销；确认后账号禁用，并按第 8 节匿名化非必要个人字段。

### 4.2 社团

- 学生可提交社团申请，名称在非归档社团中唯一；申请必须包含名称、类别、简介和申请理由。
- 申请人不能同时拥有另一条待审社团申请；是否允许一人担任多个社团主席由全局配置控制，默认不允许。
- 学校管理员批准时创建有效社团、主席成员关系和审计记录，操作必须原子化。
- 驳回必须填写原因，申请人修改后可以重新提交。
- 主席可发起注销，学校管理员终审；归档后历史活动、财务和审计仍可查询，不能硬删除。
- 主席可发起暂停或恢复申请，学校管理员审批；暂停期间禁止新活动、招募和经费申请，已有活动由管理员逐项取消或允许完成。
- 主席移交必须由当前主席指定一名有效成员、候选人确认、学校管理员复核，并在单一事务中完成新旧岗位变更。
- 只有已批准社团可发布活动、招募成员和提交经费申请。

### 4.3 成员与部门

- 学生对同一社团最多有一条有效或待审成员关系。
- 加入申请可由主席或副主席审批；申请人可在审批前撤回。
- 主席不能直接退出，必须先完成主席移交；最后一名主席角色不可删除。
- 移除成员和拒绝申请必须记录理由；历史记录保留。
- 部门名称在社团内唯一；有有效成员的部门删除前必须迁移成员或停用部门。
- 副主席不能任命或移除主席，也不能突破主席、副主席数量上限。

### 4.4 活动、报名与签到

- 活动开始时间必须早于结束时间，报名截止时间不得晚于开始时间，人数上限必须大于 0。
- 仅社团负责人可提交活动，学校管理员批准后才对外发布；驳回必须填写原因。
- 报名仅在已发布、未截止且名额可用时受理。需要审批的活动先进入待审，否则直接成功。
- 同一用户对同一活动只有一条报名记录；取消后可在截止前重新报名。
- 名额扣减在事务内完成，并发报名不得超卖。取消已批准报名时释放名额。
- 签到码是短时、一次活动专用的随机令牌，不包含用户或活动敏感信息；默认有效 5 分钟，可轮换。
- 只有报名已批准的用户可签到；同一用户只能成功签到一次。人工补签必须填写原因并审计。
- 活动结束后负责人可提交总结；只有实际签到者可评价，且每人最多一条评价。

### 4.5 财务

- 金额必须大于 0，统一使用人民币和两位小数；不得使用浮点数存储金额。
- 经费流程为草稿 → 已提交 → 社团初审 → 学校终审 → 已支付/已报销，任一审核节点均可驳回。
- 申请创建者不能审批自己的申请；主席创建的申请跳过社团自审，直接进入学校终审，但仍记录规则来源。
- 驳回、撤回和取消均保留历史，已支付记录不可修改金额或硬删除。
- 附件仅允许配置的图片和 PDF 类型，校验内容类型、扩展名、大小与随机存储名。
- 报表按社团和日期范围统计已批准或已支付记录，导出受同样权限和筛选条件约束。
- 首版预算按“社团 + 自然年度”设置批准额度；提交经费时校验已占用加本次金额不超过额度，驳回或撤回释放占用，终审批准后转为实际支出。
- 学校管理员在终审后登记 `Paid`（拨款）或 `Reimbursed`（报销）结果、时间和外部凭证编号；结果登记人不能是申请人。

### 4.6 通知、评价与审计

- 系统通知可定向到用户、社团成员或全校用户；读取状态按接收人单独记录。
- 学校管理员可发布全校通知，主席/副主席可发布所属社团通知，部门负责人可发布本部门通知；发布者必须提供标题、正文和目标范围。
- 通知发送失败不得回滚主业务事务，可通过事务外盒重试；首版站内通知至少保证最终可见。
- 活动评分为 1 到 5 分，评价内容最多 1000 字；用户可在 7 天内修改自己的评价。
- 反馈允许学生查看自己的处理状态，管理员回复时产生通知。
- 管理员可隐藏违反规范的评价但不能篡改原文，隐藏操作和原因必须审计；社团负责人只能公开回复所属社团评价。
- 登录、权限变更、审批、签到、财务变更、导出和用户冻结必须写不可由普通业务用户修改的审计日志。
- 审计日志至少包含操作者、动作、对象类型与编号、时间、结果、关联请求编号；敏感字段必须脱敏。

## 5. 状态机

### 5.1 社团申请与社团

社团申请：`Draft → Submitted → Approved | Rejected | Withdrawn`，`Rejected → Draft`。Approved 为申请终态；批准事务同时创建状态为 Active 的社团和主席成员关系。

社团：`Active → SuspensionRequested → Suspended | Active`，`Suspended → ReinstatementRequested → Active | Suspended`，`Active | Suspended → ClosureRequested → Archived | 原状态`。竖线右侧的“原状态”表示驳回后恢复申请前状态；Archived 为终态。

### 5.2 成员关系

`Pending → Active | Rejected | Withdrawn`

`Active → Exited | Removed`

Exited、Removed 后可重新申请并产生新的成员关系记录，旧记录保持不变。

### 5.3 活动

`Draft → Submitted → Approved | Rejected | Cancelled`，`Rejected → Draft`。

活动创建者在批准后发布：`Approved → Published → InProgress → Completed`。Approved 或 Published 可在开始前由创建者申请取消，学校管理员确认后转为 Cancelled；学校管理员也可因安全原因直接取消并填写原因。开始和结束状态由定时任务推进，授权负责人只能在时间守卫允许时人工补偿推进。

### 5.4 报名

`Pending → Approved | Rejected | Cancelled`，`Approved → CheckedIn | Cancelled | Absent`。用户在截止前取消后重新报名会复用同一逻辑报名记录、增加新的状态历史，并根据活动配置进入 Pending 或 Approved；数据库仍以活动和用户唯一约束防重。CheckedIn、Rejected、Absent 为该次报名周期终态。

### 5.5 财务申请

普通申请人：`Draft → ClubReviewPending → SchoolReviewPending → Approved → Paid | Reimbursed`。

主席申请人：`Draft → SchoolReviewPending → Approved → Paid | Reimbursed`，规则引擎记录跳过社团初审的原因。ClubReviewPending 和 SchoolReviewPending 可转为 Rejected；Rejected 可复制为新草稿并保留关联；Draft 和审核中状态可由创建者转为 Withdrawn。Paid、Reimbursed、Withdrawn 为终态。

## 7. 用例规格与验收场景

### 7.1 通用前置与后置规则

- 除公开浏览和注册登录外，参与者必须处于有效登录状态。
- 所有修改命令均校验主体、资源、动作、作用域、状态与并发版本；失败不产生部分写入。
- 成功修改后返回新的资源状态，产生适用的审计和通知；失败采用稳定错误码并保持原状态。
- 表中 `AC-编号` 对应至少一条自动化验收测试；“拒绝”均要求返回适用错误码且数据不变。

### 7.3 Given-When-Then 判定样例

每个 `AC-*` 都按同一结构实现。代表性场景如下，其余场景以第 7.2 节的主流程和关键异常分别生成正反测试：

- `AC-CLUB-01`：Given 学生无待审申请且名称未占用，When 提交申请并由非申请人的学校管理员批准，Then 申请为 Approved、社团为 Active、申请人成为唯一主席，三者在同一事务提交并记录审计。
- `AC-ACT-02`：Given 活动仅剩 1 个名额，When 两个不同用户并发报名，Then 恰好 1 条报名获批且已批准数不超过上限。
- `AC-ACT-03`：Given 用户报名已批准且签到码在有效期，When 首次提交该码，Then 状态变为 CheckedIn；When 再次提交同码，Then 返回幂等成功或已签到错误且不增加记录。
- `AC-FIN-02`：Given 申请人为副主席，When 申请人本人尝试社团初审，Then 返回职责分离错误且状态仍为 ClubReviewPending。
- `AC-FILE-01`：Given 文件扩展名为 `.jpg` 但内容是可执行文件，When 上传，Then 返回类型校验错误且存储中不存在该文件。

| 编号 | 类别 | 可测要求与通过条件 |
|---|---|---|
| UX-01 | 可用性 | 核心列表和表单具备加载、空、错误、无权限状态；删除、驳回、冻结、取消和财务结果登记二次确认 |
| PERF-01 | 性能 | Release 模式，4 核 CPU/8GB 内存应用节点、同局域网 SQL Server；数据集含 1 万用户、200 社团、2000 活动、10 万报名；预热 2 分钟后以 200 虚拟用户、70% 读取/30% 写入运行 10 分钟，读请求 P95 <500ms、写请求 P95 <1s、错误率 <1% |
| SEC-01 | 安全 | 对象级授权反向测试全部通过；登录和敏感接口限流；秘密来自环境或秘密存储；生产 HTTPS、安全响应头和受限 CORS；依赖高危/严重漏洞为 0 |

| MAINT-01 | 可维护性 | 前后端格式与静态检查通过；OpenAPI 与实际端点一致；核心状态机分支具有单元测试，公开端点具有集成测试 |
| PORT-01 | 可移植性 | 空环境可用 SQLite 初始化演示；同一迁移模型可在 SQL Server 初始化并通过数据库集成测试 |
| COMP-01 | 兼容性 | 发布清单锁定测试日期当天 Chrome、Edge、Firefox 最新稳定版及前一主版本；移动测试锁定 Android Chrome 与 iOS Safari 最新稳定版，主流程全部通过 |
| REC-01 | 恢复 | 生产每日备份，RPO ≤24h、RTO ≤4h；在发布候选环境完成一次从备份恢复并校验用户、社团、活动和财务抽样 |
| OBS-01 | 可观测性 | 每个响应含关联编号；结构化日志可按编号定位请求；存活、就绪和数据库健康检查可被监控独立识别 |

## 9. 数据保留与删除

- 业务时间统一以 UTC 存储，界面按学校时区显示。
- 用户注销采用匿名化和禁用，不级联删除历史财务、活动和审计记录。
- 已归档社团、已结束活动和财务记录默认保留 5 年，学校可在配置中延长。
- 普通通知默认保留 1 年；安全审计默认保留 2 年。
- 开发种子数据不得包含真实学生隐私。
