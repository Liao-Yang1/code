# 项目治理与质量门禁

## 1. 目标

本文件定义高校社团管理信息系统从理论设计到代码交付的统一质量门禁。任何“通过”都必须有可追踪的审查记录、问题关闭证据和验证结果，不能仅以重复阅读代替审查。

## 2. 基线结论

- 原项目定位为不可运行的早期原型，不把原总结中的“已实现”作为验收依据。
- 原型后端解决方案未引用实际项目，直接构建项目存在语法错误。
- 原型前端缺少构建入口且引用不存在的页面，生产构建失败。
- 原型缺少数据库迁移、自动化测试、细粒度授权、安全密钥管理和部署验证。
- 接管后的所有完成状态以本仓库的需求追踪、自动化测试和验收记录为准。

## 2.1 Git 提交要求

- 最终仓库至少包含 40 次与本项目相关的有意义提交，目标为 50 次以上。
- 提交按治理、需求、架构、各业务模块、测试、修复和部署等可独立复核的里程碑拆分。
- 使用 `docs:`、`feat:`、`fix:`、`test:`、`refactor:`、`build:`、`ci:`、`chore:` 等规范前缀。
- 禁止使用空提交、只改空白或先拆后合等方式凑数；每次提交应能说明一个明确增量。
- 理论和实现门禁的受审版本使用提交哈希固定；审查修复必须形成独立提交。

## 3. 阶段与门禁

| 阶段 | 主要交付物 | 进入下一阶段的条件 |
|---|---|---|
| G0 基线审计 | 现状、风险、范围、审查规则 | 高风险事实已确认并登记 |
| G1 需求与领域 | 用例、角色权限、业务规则、状态机、验收标准 | 独立审查连续 3 轮无新问题 |
| G2 技术设计 | 架构、数据模型、API、安全、测试、部署设计 | 独立审查连续 3 轮无新问题 |
| G3 理论总审 | 全部设计文档和需求追踪矩阵 | 独立审查连续 5 轮无新问题 |
| G4 实现 | 后端、前端、迁移、种子数据 | 每个实现里程碑构建与测试通过，且连续 3 轮独立审查无新问题 |
| G5 系统验收 | 端到端、安全、兼容性、部署和文档验证 | 阻断和高风险问题为 0，既定验收用例通过，连续 3 轮独立审查无新问题 |

## 4. 审查规则

1. 每轮必须记录审查范围、检查视角、发现、处理结果、清单覆盖率和工具证据。
2. “新问题”指此前问题清单中不存在、且需要修改交付物或明确接受风险的有效问题。
3. 同一根因的重复表述不计为新问题，但必须关联原问题。
4. 发现任何新问题时，连续无新问题计数归零；修复后重新开始计数。
5. 每轮必须切换检查视角，至少覆盖完整性、一致性、可实现性、安全性、可测试性和运维性。
6. 文案偏好或不影响正确性的建议记为改进项，不阻断连续计数；未解决的中高风险问题必须阻断。
7. 审查记录必须引用具体文件章节；代码阶段还须引用测试或命令结果。
8. 每轮以 Git 提交哈希为版本标识；尚未提交时记录全部受审文件的 SHA-256。任一受审文件内容变化都会使已有连续计数归零。
9. 一轮干净审查必须同时满足：适用清单覆盖率 100%、无新增可执行问题、当前阶段 P0/P1 为 0、既有问题均有复核关闭证据、自动检查通过。
10. 实现阶段按身份权限、社团成员、活动签到、财务通知、前端流程和最终验收划分里程碑，每个里程碑均执行完整性、一致性、安全/测试三个视角的连续 3 轮审查。

## 5. 问题等级

| 等级 | 定义 | 门禁处理 |
|---|---|---|
| P0 阻断 | 导致核心流程不可用、数据破坏或严重安全事件 | 必须立即修复 |
| P1 高 | 关键需求缺失、越权、敏感数据泄露或无法部署 | 必须在当前门禁修复 |
| P2 中 | 边界规则缺失、一致性或可测试性明显不足 | 原则上当前门禁修复 |
| P3 低 | 不影响主流程的可维护性、易用性或文档问题 | 可修复或登记接受 |

## 6. 完成定义

功能只有同时满足以下条件才标记为完成：

- 有唯一需求编号和明确验收标准。
- API、界面、权限、审计和异常路径保持一致。
- 数据库变更由迁移管理，能够从空库初始化。
- 自动化测试覆盖核心成功路径和关键失败路径。
- 没有硬编码生产秘密，没有返回密码哈希等敏感字段。
- 构建、测试、依赖审计和端到端验收均有记录。
- README 能让新的开发者在干净环境中启动系统。

## 7. 审查记录格式

审查记录统一写入 `docs/reviews/审查日志.md`，每轮使用以下字段：

- 轮次与日期
- 审查范围及 Git 哈希或文件 SHA-256
- 审查视角
- 适用清单覆盖率与工具证据
- 新问题及等级
- 已关闭问题与证据
- 剩余风险
- 连续无新问题计数
- 结论
